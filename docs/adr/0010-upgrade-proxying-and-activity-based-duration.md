# ADR 0010: Proxy protocol upgrades transparently; bound duration by activity, not a flat deadline

Status: accepted

## Decision
The edge no longer refuses HTTP protocol upgrades (`Upgrade:`/`Connection: upgrade`, including WebSocket) with `501 upgrade_not_supported`. An upgrade request is proxied like any other: validated, routed, gated, and forwarded through the tunnel; a `101 Switching Protocols` response causes the edge to hijack the public connection and the client (`client/origin`) to hold the origin connection open, then both sides pump raw bytes bidirectionally between the public caller and the origin for the life of the connection.

Alongside this, `RequestMaxDuration` (the edge's `Config.MaxDuration`) stops being a flat wall-clock cap on an entire proxied exchange. It now bounds only opening the tunnel stream (`Session.Open`), which has no activity to watch and so is the one phase a flat deadline suits. Everything after that — a request body, a response body, or an upgraded connection's bytes in either direction — is governed solely by `RequestIdleTimeout`: one shared "no progress in either direction" watchdog per exchange, touched by whichever side makes progress, that only fires on true, simultaneous inactivity. `ResponseHeaderTimeout` is unchanged in role (bounds the wait for the origin's first byte) but is no longer a child of the `MaxDuration`-bound context, so raising it alone is enough to support a slower long-poll.

## Rationale
Repository owner's decision (2026-10-01): WebSocket, SSE, long-poll and large downloads are meant to work. The multiplexed tunnel stream (`protocol/tunnel`) was already a generic, flow-controlled, independently-half-closable bidirectional byte pipe — the blocker was policy (the upfront `IsUpgrade` rejection) and the duration model (a flat per-exchange deadline that killed any exchange, upgraded or not, purely for running longer than a fixed number of minutes regardless of whether it was making progress), not the protocol. No new dependency was needed or added; the proxying approach mirrors the standard library's own pattern for this (`net/http/httputil.ReverseProxy`'s `handleUpgradeRequest`/`handleUpgradeResponse`: manual dial, raw request/response write, hijack-and-pump).

## Consequences
- `dataplane/proxy` gained upgrade-preserving header filters (`UpgradeRequestHeaders`/`UpgradeResponseHeaders`): every hop-by-hop header is still stripped except `Connection`/`Upgrade` themselves, on both the request and a `101` response.
- `client/origin.Handler` gained a manual-dial path (`serveUpgrade`) for upgrade requests only; normal requests are unaffected and still go through `http.Client`. The existing loopback-only SSRF dialer `Control` func is reused unchanged.
- `dataplane/ingress` gained a shared per-exchange `idleWatchdog` (replacing a response-only local timer) and a hijack-and-pump path (`serveUpgrade`, `copyGated`) for the `isUpgrade && resp.Status == 101` case; every other response status falls through to the existing header-copy/`pumpResponse` path unchanged, so an origin is free to decline an upgrade and answer normally.
- Trade-off accepted deliberately: removing the absolute cap on body/upgrade duration means a well-timed trickle (just under `RequestIdleTimeout` between chunks) can hold a stream open indefinitely. This was never the right knob for abuse control — per-session stream limits (`MaxStreamsPerSession`), per-connection session limits (`MaxSessions`), and per-tenant bandwidth/quota gates (`Gate.Wait`/`Account`) are unchanged and remain the actual defenses; duration limits now exist only to detect a dead/stalled peer.
- `docs/operations.md`'s known-limitations list and platform-error catalog (`upgrade_not_supported` no longer exists) are updated accordingly; raw TCP/UDP and custom domains remain explicit non-goals.
