# Results: 2026-09-21, laptop-class machine

Raw numbers from the runs described in [`../methodology.md`](../methodology.md). Read the
limitations at the end before quoting anything.

## Environment

| | |
|---|---|
| CPU | 11th Gen Intel Core i7-1165G7 @ 2.80 GHz (4 cores / 8 threads) |
| Memory | 15.7 GB total, about 4 GB free during the runs (other processes were running) |

| Go | go1.26.0 for all figures below (the repository now pins `toolchain go1.26.8`; see "Security scans") |

## 1. Added latency and throughput of a proxied request

`POST` with a 128-byte response, keep-alive HTTP/1.1 from the load generator to the edge ingress
(plain HTTP, TLS is measured separately by the tunnel handshake). Latency percentiles are computed
from every request. "Direct" is the same origin with no platform in between.

| Concurrency | Path | p50 (µs) | p95 (µs) | p99 (µs) | req/s |
|---:|---|---|---|---|---|
| 1 | direct | 35 / 36 / 37 | 60 / 61 / 64 | 91 / 101 / 109 | 25,167 / 24,496 / 23,780 |
| 1 | through platform | 161 / 167 / 174 | 339 / 352 / 370 | 499 / 505 / 533 | 5,227 / 5,108 / 4,849 |
| 16 | direct | 132 / 131 / 132 | 468 / 357 / 320 | 1,141 / 1,114 / 1,175 | 88,393 / 91,949 / 92,552 |
| 16 | through platform | 1,159 / 1,136 / 946 | 2,304 / 2,219 / 1,849 | 3,162 / 3,056 / 2,752 | 13,111 / 13,450 / 15,457 |
| 64 | direct | 499 / 502 / 497 | 1,985 / 1,703 / 1,532 | 3,947 / 4,113 / 4,222 | 93,771 / 94,236 / 96,233 |
| 64 | through platform | 3,150 / 3,159 / 3,192 | 5,765 / 5,830 / 5,849 | 7,701 / 7,911 / 7,921 | 19,481 / 19,498 / 19,234 |

(Each cell lists the three repetitions.) At concurrency 1 the platform adds a median of roughly
125 µs (161-174 µs vs 35-37 µs): a request crosses an extra HTTP server, a tunnel stream (OPEN,
DATA, OPEN_OK, HALF_CLOSE), the client's HTTP transport, and back, all on one shared CPU. Throughput
saturates around 19,000 small requests/s on this machine with the load generator competing for the
same cores.

## 2. Bulk transfer through the proxy

1 MiB request body and 1 MiB response per exchange; MB/s counts both directions (2 MiB per exchange).

| Concurrency | MB/s (3 runs) | p50 (ms) | p99 (ms) |
|---:|---|---|---|
| 1 | 416.3 / 455.3 / 425.7 | 4.8 / 4.4 / 4.8 | 9.0 / 7.9 / 7.8 |
| 8 | 611.7 / 659.2 / 646.2 | 27.0 / 25.5 / 25.1 | 41.6 / 36.0 / 42.5 |

**Limiter accuracy (measured by accident, kept on purpose).** The first bulk run used a fixture plan
of 100 MB/s. The proxy was then limited by the token bucket, and every run landed at
99.95 / 99.99 / 99.97 MB/s (1 stream) and 100.02 / 100.04 / 100.01 MB/s (8 streams): the shared bucket
held aggregate throughput within about ±0.05% of the configured rate regardless of stream count.
That run says nothing about proxy throughput, so the benchmark environment now lifts plan limits to 10 GB/s.

## 4. Idle tunnels

`TestIdleTunnels`: N distinct identities each create an endpoint, obtain a credential, complete the TLS 1.3
handshake with channel-bound proof, register, and are held idle for 20 s (keepalive pings only); then up to
200 tunnels are sampled with a real request. **The process holds both ends of every tunnel plus the control
plane**, so roughly half of each per-tunnel figure belongs to the edge.

| N | Established in | Sample requests OK | RSS above baseline | Per tunnel | Goroutines / tunnel | fds / tunnel | Idle CPU (20 s) | Buffers |
|---:|---|---|---|---|---:|---:|---:|---|
| 300 | 215 ms (1,397/s) | 200 / 200 | 60 MB | 205.1 KB | 10 | 2 | 0.006 cores | 32 KiB |
| 2,000 | 1.30 s (1,543/s) | 200 / 200 | 375 MB | 191.8 KB | 10 | 2 | 0.035 cores | 32 KiB |
| 2,000 | 1.38 s (1,449/s) | 200 / 200 | 323 MB | 165.1 KB | 10 | 2 | 0.035 cores | 8 KiB |
| **10,000** | **7.02 s (1,425/s)** | **200 / 200** | **1,592 MB** (baseline 14 → 1,606 MB) | **163.1 KB** | 10 | 2 | **0.127 cores** | 8 KiB |

At 10,000 tunnels: 100,026 goroutines, 20,017 open file descriptors, heap in use 1,254 MB, Go runtime `Sys` 1,960 MB.
**The 10,000-idle-tunnel target was reached on this machine.** All measured dimensions grow linearly with N.

## 5. Bandwidth enforcement accuracy (canonical free plan, real Docker stack)

`curl` over verified HTTPS/HTTP/2 through the Compose stack, `GET /bytes/500000`, canonical free plan
(100,000 B/s, 2 s burst): **3.003952 s** (expected `(500,000 - 200,000) / 100,000 = 3.0 s`). The integration test
`TestFreeTierBandwidthEnforced` asserts 2.7-4.1 s, and `TestConcurrencyDoesNotMultiplyBandwidth` shows four
concurrent streams sharing one budget (600 kB in about 4 s, not about 1 s).

## 6. Fuzzing

13 fuzz targets (frame decoder, stream state machine, request/response metadata, host parser, name validation,
auth key/challenge/token parsing, policy decoding, RESP reply parsing, verification-key parsing, money parsing)
were each run for 10 s, plus a 20 s follow-up on the money parser: no crashes, hangs or unbounded allocations.
**The fuzzer found one real bug**: `ParseAmount("9270000000000")` returned a *negative* amount (integer overflow
when scaling to atomic units). It is fixed, has an exact overflow check, and the failing input is kept as a
permanent regression case (`controlplane/payment/testdata/fuzz/`).

## 7. Static analysis and dependency scanning

| Tool | Result |
|---|---|
| `gofmt`, `go vet` | clean |
| `go test -race` | clean (whole suite, repeated runs) |
| `staticcheck` (honnef.co/go/tools v0.8.1) | 2 findings in test code (unused field, dead assignment); fixed; clean afterwards |
| `govulncheck` with go1.26.0 | **18 standard-library vulnerabilities reachable** (GO-2026-4599 ... GO-2026-6218 in `crypto/tls`, `crypto/x509`, `net/http`, `net/url`, `net`, `os`, `encoding/asn1`, `net/textproto`), all fixed in go1.26.1-go1.26.6 |
| `govulncheck` with go1.26.6 and go1.26.8 | **No vulnerabilities found** |
| Third-party Go modules | none |

Action taken: `go.mod` pins `toolchain go1.26.8` and the Docker builder uses `golang:1.26-alpine`
(go1.26.8), so a stale local toolchain cannot silently build the vulnerable standard library. The benchmark figures
above were produced with go1.26.0 (before the pin); the runtime paths involved are the same, but re-run them on
your toolchain before comparing.

## 8. Limitations

Loopback only; load generator shares the CPU with the system under test; idle-tunnel cost includes both tunnel ends
and the control plane; the machine had only about 4 GB free; no WAN, packet loss, multi-machine, soak or real-origin
testing was done; percentiles at high concurrency include queueing inside the shared process; 10,000 is the highest
count exercised, not a capacity claim. No result here was tuned to look better than the run that produced it.
